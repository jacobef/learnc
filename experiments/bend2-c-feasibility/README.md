# Bend 2 and a many-file C compiler: feasibility experiments

This directory contains experiments, not a C compiler. It does not change cBoxes.

**Start with [the findings](FINDINGS.md)** for conclusions and selected measurements.
[Full tables](results/SUMMARY.md) include sample ranges and every configuration.

The question is whether Bend 2's CPU/GPU parallelism could make a compiler faster
on projects containing very many C files. We separate three possible advantages:
parallelizing compiler work, improving its representation, and amortizing compiler
process startup across files. A win in one is not evidence for the other two.

## What actually runs in Bend

`frontend.bend` tokenizes real ASCII C source into a token list. In `lex` mode it
consumes that list into an order-sensitive per-file checksum. In `fold` mode it
recognizes `return` and evaluates fully parenthesized unsigned decimal expressions
containing `+`, `*`, and `^`, using a stack and C's modulo-2^32 arithmetic. Both
modes fork over a balanced binary tree of independent files and sum their results.
The parser is deliberately restricted to the generated valid subset; it does not
validate arbitrary C. Tokenization is common to both stages, so **fold includes
lexing**. This is a plausible front-end kernel, not emitted machine code.

The array variant is generated by `array_source()` in `experiment.py`. It uses
owned `Array<U32>` source storage instead of a linked list, preserving the token
list and expression-folding algorithm. Each source byte occupies a 32-bit array
slot, rounded to a power-of-two capacity. It does not use unsafe shared arrays.
Both variants use checked terminating recursion; neither disables Bend's checker.
No formal correctness proof of the compiler or kernels is claimed.

`loader.c` and `array-loader.c` are FFI **input adapters**, not compiler kernels.
They deserialize the same source bytes from a packed corpus into Bend-owned values.
Lexing, token handling, arithmetic folding and parallel traversal all execute as
compiled Bend code. This bypasses the small standard library's file API and
isolates input conversion. Its cost is measured separately. Packing sources is
not included in kernel timing. The full compiler would still need to discover,
read and preprocess files, emit objects, and link.

`native.c` performs the same lexical/token/fold work using idiomatic compact C
arrays. Ten pthread workers dynamically claim whole files; the one-thread case
avoids creating a thread. This is a useful efficient baseline, not a claim that
both representations and allocation algorithms are identical. C appends tokens
in source order; Bend's linked token list is built backward and reversed.

## Corpora and correctness

All sources are generated deterministically from Python seed 20260917. Decimal
constants and operators vary. Function names are unique across the project; there
are no includes, comments, macros, strings, global data or cross-file references.
The restricted language is intentionally small enough to independently check.

| Corpus | Files | Functions | Source bytes | Purpose |
|---|---:|---:|---:|---|
| smoke | 16 | 64 | 11,582 | Correctness and backend validation |
| uniform | 4,096 | 16,384 | 3,004,080 | Balanced file-level parallelism |
| many | 16,384 | 16,384 | 1,949,025 | Very many tiny translation units |
| chunky | 1,024 | 32,768 | 6,003,910 | More work per leaf |
| skew | 4,096 | 20,224 | 3,453,760 | 256 large files, 3,840 tiny files |

In `skew`, a large file contains 64 functions and a tiny file one. The same files
are tested with large files clustered together and interleaved evenly. Only their
order changes; independent expected checksums remain identical. This compares
scheduling/layout, not different programs. Other corpora differ in both work and
file count and are **not** a strong-scaling series.

Python independently generates the expression result while constructing its
expression tree. A separate regex tokenizer computes expected token checksums.
Every measured C/Bend/Metal run must match the whole-corpus checksum, including
its warm-up. Clang compiles and runs samples selected across each corpus, checking
actual unsigned C evaluation against the generator. The process-per-file Clang
reference compiles every translation unit. Aggregate 32-bit checksums are regression
checks with possible collisions, not a proof of per-token/per-file equivalence.

## Measurement protocol

`results/kernels.jsonl` preserves individual samples. Each of five fresh processes
runs an untimed first load/kernel, then a second timed load and kernel. Timings use
monotonic microsecond clocks. The loader time includes reading the packed file and
constructing source storage; it excludes runtime startup. The Bend kernel timer
includes one checksum print, generally a few microseconds. Kernels consume their
inputs; the second run receives newly deserialized data. Each configuration also
has a discarded process-level warm-up. Configuration order is shuffled per round.

GPU runs explicitly require `--gpu on`; CPU runs use `--gpu off`. Native Metal
archives are built before the final suite. The first GPU invocation in each
process initializes the pipeline; it is excluded from the reported steady-state
kernel but included in process wall time. A missing GPU causes failure instead of
silently falling back to the CPU. Metal execution requires host device access,
which was unavailable inside the filesystem sandbox and was granted for the runs.

`wall_ms` in the final kernel results includes process startup, **two complete
passes**, output and shutdown. It must not be interpreted as a one-pass time.
Do not add median load and median kernel and call that a measured end-to-end time.
The earlier `first-launch.jsonl` is retained separately: those runs had one pass,
no in-process warm-up, and no prebuilt Metal archive. They include GPU initialization
and are diagnostic cold-process measurements, not final steady-state samples.

`results/clang.jsonl` uses a Python ten-worker launcher, one Clang process per `.c`
file, with all exit statuses checked. Syntax-only and object builds are timed
separately, with three full-project samples each; filesystem caches are warm.
Object output files are written and overwritten between trials, not read from a
compiler cache. Linking is excluded. Python process-dispatch overhead is included;
this is not a benchmark of a tuned Ninja build.

The unity control concatenates the exact definitions into one translation unit
before timing Clang. Unique global names and absent headers make that safe **for
this corpus only**. It preserves the generated functions but changes the compilation
boundary. It is a control for batching opportunity, not a universally equivalent
transformation of arbitrary C projects.

## Reproduce

Use an Apple Metal machine, current Node with direct TypeScript support, Python 3,
and Apple Clang 17 (or a compatible Bend-supported native compiler). On other
hardware, CPU experiments can run, but the default GPU assertions must be adapted
explicitly and cannot be represented as Metal results.

```sh
git clone https://github.com/bendlang/bend.git /tmp/bend2-toolchain
git -C /tmp/bend2-toolchain checkout e6676b080f25b1bc1bf5b5b7d7a17e22f8022599
cd experiments/bend2-c-feasibility
python3 experiment.py generate
python3 experiment.py build --toolchain /tmp/bend2-toolchain
python3 experiment.py validate
python3 experiment.py bench --repeats 5
python3 experiment.py build --toolchain /tmp/bend2-toolchain --arrays
python3 experiment.py bench --cases smoke uniform many chunky skew --repeats 5 --arrays
python3 experiment.py clang --cases uniform many --workers 10 --repeats 3
python3 experiment.py unity --cases uniform many --repeats 3
python3 experiment.py pack --cases uniform many --repeats 5
python3 report.py
```

The benchmark appends JSONL output; move existing result logs aside before reruns
if you want separate sample sets. Generated source files, objects, binaries and
Metal archives are confined to ignored `.work/`. The upstream toolchain is external
and pinned, rather than vendored. Source and corpus hashes live in `results/`. Unity objects were additionally
checked with `llvm-nm --defined-only --extern-only`; each retains all 16,384
expected external functions. That check is saved in `unity-symbol-validation.json`.
